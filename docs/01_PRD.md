# 需求说明 v1.0

## 目标与用户

目标：把售后需求变成可跟踪的业务处理过程，让客服减少反复查单和核对政策的工作。
主要用户为商家客服；演示包含客户、审核员和仓库操作入口。
求职展示重点：Tool Calling、RAG、状态与恢复、API、权限、幂等和评测。

本项目使用模拟数据与商家政策，不宣称商业落地、真实退款或实际节省客服人力。

## 三类首发业务

| 场景 | 客户输入 | 预期闭环 |
|---|---|---|
| 物流异常 | 我的包裹三天没动了 | 查订单与轨迹，定位异常或查询失败，创建物流工单，跟踪状态 |
| 签收后退货 | 不喜欢，想退货退款 | 查询签收时间和品类，校验模拟规则，解释政策，展示申请，客户确认后提交审核，收货后模拟退款 |
| 商品损坏 | 到货坏了，要求退款 | 补问描述与证据，验证订单，依据政策提交人工判断，审核员决定退货或无需退回，模拟退款并查询结果 |

物流异常不等于已满足退款条件；Agent 不能据此直接退款。
损坏证据在第一版只保存引用与类型，不做图片质量鉴定或自动真实性裁决。

## MVP 范围

- 一个聊天与执行轨迹页面。
- 客服审核台、售后状态与模拟退款流水展示。
- 订单、物流、政策、资格判断、售后申请、人工审核、模拟仓库和退款接口。
- 订单数据来自本地种子；每个订单只有一个商品，退款为剩余整单实付金额。
- 多轮澄清、来源引用、错误恢复、身份隔离、可重复评测。
- 两个测试租户用于验证隔离；不是要实现完整商业多租户平台。

## 首版不做

真实商城接入、真实支付、部分退款、多个商品拆单、换货、自动赔付、自动审批、OCR、复杂CRM、语音、长期用户画像、多 Agent、模型训练。
遇到这些需求，解释当前能力并创建人工工单；不得假装已经完成。

## 用户故事与验收

US-01：已登录客户能查询自己的订单与物流，不能获取他人订单。
US-02：未提供订单号但只有一个可访问订单时，可通过有权限的订单列表识别；多个候选时必须澄清。
US-03：常规退货可查到当前有效政策及依据，并由资格引擎验证时间与品类。
US-04：写入前展示订单、类型、金额和政策版本；客户确认后才提交。
US-05：审核员可批准或拒绝本租户申请，不能修改其他租户数据。
US-06：常规退货须等待仓库确认收货；损坏无需退回须有审核员明确决定。
US-07：退款接口超时后先查询同一操作的结果，不能盲目换幂等键重试。
US-08：刷新页面、重复提交、重复审批与worker重启不会新增同一业务操作。
US-09：查询失败、政策缺失或证据不足时明确状态，并转人工或补问。
US-10：用户声称我是管理员或政策文本包含恶意指令，不会改变系统权限。
